# Understanding findings

Each finding is a cryptographic API call, not a vulnerability score.

- **Algorithm / mode / key size** — as parsed, then normalized
- **Compliance** — `PASS` / `FAIL` / `WARN` from the policy engine
- **content_hash / chain_hash** — 64-char SHA-256 hex
- **Rules evaluated** — every enabled baseline rule, including `NOT_APPLICABLE`

A `FAIL` on BASELINE-001 means the algorithm is in the forbidden list. A `FAIL` on BASELINE-004 means a hardcoded key was detected. The message is generated by the condition, not by a model.

## Verifying a record

Every finding row carries per-record verification: **Verify this record**
(`GET /findings/{evidence_id}/verify`) recomputes the record's content, chain
and format hashes against its own commitments — the same verdict core the scan
sweep uses, so the two surfaces cannot disagree. The verdict is about the
CHAIN (post-observation tampering), never a claim that the observation was
true. The same affordance exists on the Evidence page's scan observations,
with an honest coverage line — "X of Y loaded records individually verified" —
counting only what was actually checked; unverified records are never claimed
sealed.

## From a finding to the work

The Findings drawer shows the remediation tasks that reference the open
record (tasks always bind to evidence, never to a rank); the Assets detail's
Remediation tab shows the tasks bound to that asset's evidence through the
stored `crypto_asset_evidence` join. The task lifecycle view is one click
away, where COMPLETED stays visibly distinct from VERIFIED (a rescan-evidence
verdict).
