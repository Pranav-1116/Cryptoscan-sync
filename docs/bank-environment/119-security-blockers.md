A review named eight security properties a bank must be able to test before it
runs this platform. All eight are now answered by **execution** — each by its own
drill, each with a verdict that a re-run can overturn. Nothing here is a plan;
every claim below is regenerated by a script.

| 4 | Secret management | **closed** — 6 pass · 0 partial · 0 fail (the console token in `localStorage` was found, then fixed) | [123](123-secret-management.md) |
| 5 | Command execution — collector input must never become a command | **closed** — 4 pass · 0 partial · 0 fail, **3 injection defects found and fixed** | [122](122-command-execution.md) |
| 6 | SSRF | **closed** — 6 pass · 0 partial · 0 fail: policy plus rebinding, redirect, direct-socket and guard probes | [125](125-ssrf.md) |

Grades are the same three used everywhere in this series: **PASS** (measured, and
the measurement can fail), **PARTIAL** (measured, with a named property not
exercised), **FAIL** (a probe answered wrong). `UNPROVEN` is never a pass.

## 1. Authentication — **8 PASS · 0 PARTIAL · 0 FAIL**

`scripts/auth_qualification.py` drives the real auth router, the real session
manager and the real user store through the production session gate, over HTTP,
against a temporary database with PBKDF2 hashes at the configured work factor.

| Question | Verdict | What was executed |
|---|---|---|
| login | **PASS** | correct credential mints a token; wrong password, unknown user and empty password all refused; unknown user and wrong password answer **identically** (no enumeration) |
| session / token | **PASS** | token accepted at the gate; tampered payload refused; token signed by another deployment refused; missing and malformed credentials refused; a role header does not change identity; cookie is `HttpOnly` + `SameSite=Lax` |
| MFA | **PASS** | password alone mints **no** token and returns `mfa_required`; the challenge token is **not** accepted as a session; wrong TOTP refused; correct TOTP mints a session; a recovery code works once; a **TOTP is single-use** — the same code presented twice is refused, and a code from an already-consumed step is refused |
| expiry | **PASS** | an expired session is refused; a live one is accepted; the token carries an expiry inside the configured window; an MFA challenge is not a session; a session **idle** past `SESSION_IDLE_MINUTES` is refused while its absolute expiry is still hours away; a freshly used one is accepted, and using a session moves its idle clock forward |
| revocation | **PASS** | logout kills the token at the gate; the revocation is **store-backed** (a second client sees it); revoke-all ends other sessions |
| password policy | **PASS** | short and single-class passwords refused 422; a strong one accepted; the stored credential is `pbkdf2_sha256` and does not contain the plaintext; a plaintext stored secret never verifies in production; public registration cannot ask for a privileged role; a password containing the **account's own name** is refused; **cannot be cycled back** — the replaced hash is remembered (5 deep, hashes only) and reuse is 422; a strong-shaped password listed in the configured **breach corpus** is refused, and production without a corpus logs a named gap |
| lockout | **PASS** | every failure refused; the correct password is refused **while locked**; the lock lives in the users table so a fresh service object still refuses; other accounts unaffected; failures audited; **spraying is stopped per source** — after `LOGIN_SOURCE_MAX_FAILURES` failures from one address even a correct password is refused, and another address is unaffected |
| credential handling | **PASS** | the password is never echoed; `/auth/me` carries no hash and no MFA secret; an error body does not repeat the attempted password; a token in the query string grants nothing; with the real access-log middleware in front, neither the attempted password, the account password nor the session token appears in any emitted log record |

**All five PARTIALs were closed in code, then re-measured** (guide 120,
`scripts/auth_qualification.py`; unit pins in
`services/api/tests/unit/test_auth_hardening.py`):

* *single-use codes* — `totp.verify_step()` now returns which time-step a code
  belongs to and `user_sessions.last_totp_step` refuses a step at or below the
  last one used, so an observed code cannot be replayed inside its ±30 s window;
* *idle expiry* — `api/security/session_policy.py` adds a second clock
  (`SESSION_IDLE_MINUTES`, tracked in `user_sessions.last_seen_at`, refreshed at
  most once a minute). Absolute expiry still wins; activity cannot resurrect an
  expired session;
* *reuse and breach* — `db:user.password_history` keeps the five previous
  **hashes** and `set_password` pushes the replaced one in; `validate_password_policy`
  refuses identity tokens, history hits, and any digest in the operator-supplied
  `PASSWORD_BREACH_CORPUS` (`api/security/breach_corpus.py`);
* *per-source velocity* — `UserRepository.count_recent_source_failures` counts
  audit failures per address inside `LOGIN_SOURCE_WINDOW_SECONDS` and
  `AuthService` refuses the source before the password is read, which per-account
  lockout can never do;
* *log redaction* — measured here, in this drill, with the product's own
  access-log middleware in front, instead of deferred to another guide.

One residual is stated rather than hidden: the corpus is operator-supplied, so
this drill proves the **check** works, not that any particular list is current.
Keeping the feed fresh is an operational obligation, and the startup warning
names it when it is absent in production.

## 2. Authorization — **9 PASS · 0 PARTIAL · 0 FAIL**

`scripts/authorization_boundaries.py` reads the boundary each operation
**declares** from its dependency tree, then sends the request as Admin, Auditor
and Viewer through the real app and compares the two. It executed **1,617
decisions** across **1,225** operations.

| Question | Verdict | Executed result |
|---|---|---|
| are the three roles distinct? | PASS | `admin → superadmin`, `viewer → readonly`, and viewer permissions ⊂ auditor ⊂ admin (strictly) |
| can an **Admin** cross? | PASS | 0 escapes |
| can an **Auditor** cross? | PASS | 0 escapes |
| can a **Viewer** cross? | PASS | 0 escapes |
| declared = enforced? | PASS | 1,617 decisions, **0 violations**, 0 over-tight (5 handler-level refusals reported separately: a public path verifying its own HMAC signature, and tenant guards that refuse a platform principal) |
| is it enforced without a session? | PASS | **0 of 562** gated writes answered without a token |
| does a forged token get in? | PASS | **0** writes accepted a token signed by another deployment |
| can a **Viewer** write anywhere? | PASS | **40 of 40** sampled session-only writes refused for the viewer **and** for the auditor, at the gate; **40 of 40** reached the handler as a writable role (the control) |
| is the *target* authorized server-side? | PASS | no scope fails closed (409); a `/8`, `169.254.169.254` and `127.0.0.1` are refused 422 when saving a scope; a host or CIDR outside the approved scope is refused even for an admin; a source scan of `/etc` is refused |

**The instrument proves it can fail.** The comparator is exercised with a
requirement that forbids a role and a decision that allows it, and it reports the
violation; the same comparator is then used for every decision above.

**Two things the drill learned by doing it, both worth recording.**

- Sweeping every write with an empty body **engaged the platform's emergency
  stop**. The sweep had POSTed to `/network/crypto-stop`, and every later
  collection answered `409 network_observation_stopped` — a drill that changed
  what it measured. Destructive routes are now named and skipped, and the skip is
  printed in the report rather than being invisible.
- A 403 is not automatically a boundary violation. Routes guarded by **tenant
  membership** refuse a platform principal who belongs to no organisation, which
  is the tenancy boundary working. Those routes are counted and excluded from the
  role comparison, and the count is printed.

**The PARTIAL is closed, and it was closed by enforcing a rule the catalog
already stated.** The catalog describes `readonly` as "dashboard view only" and
`auditor` as "read-only access to all reports"; 180 writes reachable by any
session made both descriptions false. `api/security/write_authority.py` now
refuses a human session whose roles are **all** read-only on every mutating
method, before the route runs, for these reasons:

- **it is enforced once, not per route.** A new router cannot become writable
  for a viewer by forgetting a dependency — the failure mode that produced the
  180.
- **durable roles, not token claims.** The check reads the role store, so a
  token minted before a demotion stops writing at the demotion, not at expiry.
- **two exemptions, both narrow.** Session lifecycle (`/auth/*`: rotating your
  own password, enrolling MFA, ending your own sessions) and path suffixes that
  *record a signed attestation* (`/reviews`, `/truth/approve`). An auditor is the
  role that signs those — independence is the product's whole point — and every
  such handler still enforces its own reviewer assignment, which this drill's
  §6/§7 rows and the assurance suite measure.
- **machine credentials are untouched.** An API key's authority is its own
  policy (`allowed_methods`, `allowed_ips`, quota, role list), measured in guide
  124; a user-role rule applied to a collector key would break ingestion without
  tightening anything.

The 295 operations that still declare no *route-level* role are recorded in
`102-authenticated-only-writes.json` with the reason and the writable roles they
now require — a policy, not an open door.

**What this changes for the console, stated rather than discovered.** The web
UI still renders write controls for a read-only user; pressing one now returns
`403 WRITE_FORBIDDEN` and the message the API sends — "This account has
read-only access; the operation changes state and requires a role that may
write" — is surfaced by `frontend/src/lib/api.ts`, which already lifts a JSON
`detail` into the error it shows. Hiding or disabling those controls per role is
a UI follow-up, not a security gap: the server refuses the call, which is the
part that matters.

## 3. Agent machine identity — **7 PASS · 0 PARTIAL · 0 FAIL**

Guide 119 originally recorded the gap as three facts that were never joined. They
are joined now: `api/security/agent_identity.py` reads the peer certificate the TLS
stack verified, turns it into an **SPKI** fingerprint (SHA-256 over the public key,
so a reissued certificate keeps the machine's identity and a new key never inherits
it), resolves it against a registry of agents, and the ingestion route refuses an
observation whose signature is not the key registered for that agent.
`api/middleware/agent_identity_middleware.py` attaches the identity to the request
and refuses the ingest surface outright when no registered agent is proved — inert
unless `CRYPTOSCAN_REQUIRE_AGENT_IDENTITY` is set. Full evidence:
[124](124-agent-identity.md).

| Question | Verdict | Executed result |
|---|---|---|
| can the boundary read the identity the TLS handshake proved? | PASS | a **real** TLS handshake (site CA, client certificate) — the server's `getpeercert` yields the certificate, and its SPKI fingerprint matches the client's |
| is an unregistered certificate refused? | PASS | registered → resolves; same-CA but unregistered → no agent; duplicate fingerprint → refused; malformed registry → refused, not "trust all"; empty registry → refuses everything |
| must the signature be the key registered for that agent? | PASS | bound key accepted; another agent's key refused; unsigned refused; swapped embedded key refused |
| does the middleware refuse an ingest request with no registered agent? | PASS | registered certificate 200; garbage 403; no certificate 403; a non-ingest path unaffected; inert when the requirement is off |
| does the ingestion route refuse a signature that is not the agent's? | PASS | bound 200; foreign key **401 `signature_not_bound_to_agent`**; unsigned 401; identity absent 403 |
| does certificate → agent → signature hold, and does the replay fail? | PASS | honest chain ends at authenticity `VALID`; the attack this closes — a valid certificate for machine A carrying machine B's signature — is refused |
| can each instrument fail? | PASS | wrong key reported unbound, garbage certificate rejected, unknown fingerprint returns no identity |

**What remains a deployment property, stated rather than assumed.** The
application half is proved; whether the TLS server in front of the API exposes its
peer certificate to the application depends on the terminator. Two supported
shapes: terminate TLS in-process (the ASGI `tls` extension carries the chain), or
declare the terminator (`CRYPTOSCAN_TRUST_MTLS_TERMINATOR=1`) and let it forward
the fingerprint — and then the terminator, not this process, is the trust boundary.
The registry is a deployment file; who may write it is the same trust the CA
already has.

## 4. Secret management — **6 PASS · 0 PARTIAL · 0 FAIL**

`scripts/secret_management.py` puts a distinctive canary through four paths — a
log line, an error response, an access line, the console's storage — and scans
source for credential shapes. Full evidence: [123](123-secret-management.md).

| Question | Verdict | Executed result |
|---|---|---|
| is a credential committed to the tree? | PASS | 0 findings across 7 patterns in product code; **13 allow-listed with a written reason**, and 16 fixture hits in `scripts/` listed separately rather than silently excluded |
| does a secret written to a log come back out? | PASS | a `password`/`api_token`/`private_key` field is masked, **and** so is a secret interpolated into the message text (`password=hunter2` → `password=[REDACTED]`) — the key-based gap this row first reported; the control proves the canary is visible when redaction is off |
| can a failing call return a credential to the caller? | PASS | an unhandled driver error carrying `postgresql://svc:<canary>@…` returns a body without it, while a hand-written detail is returned verbatim (the control that proves the check is not passing on empty bodies) |
| does the request log record the credential it was given? | PASS | `Bearer`, `X-API-Key` and cookie canaries absent from the access line |
| does the console keep a session where a script can read it? | PASS | the token is held in memory; only a non-secret `zelinx_signed_in` flag survives a reload, and a planted `localStorage` token in the negative control is still detected |
| does a credential travel in a query string? | PASS | none — the invite page reads its one-time token from the URL **fragment**, which is never sent to a server nor carried in a `Referer` |

**The FAIL was the finding, and it is fixed.** The backend already sets an httpOnly
`cryptoscan_session` cookie and verifies the session with `GET /api/v1/auth/me`,
so the `localStorage` copy was redundant *and* exposed: any XSS on the console could
read a bearer token. `lib/api.ts` now holds the token in memory, purges the legacy
key on load, and exposes `hasSession()` for the UI gates that used to ask
`getToken()` — the SSE stream and the worker-fleet probe connect on the cookie after
a reload instead of going quiet. Two gaps closed with it: the invite token is read
from the fragment (never from the query string), and the log pipeline scrubs
credential *shapes* in message text, so a value interpolated into a line is masked
as well as a value passed under a sensitive key.

Three bugs the change surfaced, all fixed: the Resilience page was reading a
`zelnx_token` key that never existed (a typo of `zelinx_token`, so the PDF download
never sent a credential), three cross-tab listeners were keyed on the removed
token entry, and 18 frontend test files seeded a session by writing that key —
they now call `setToken()` like the product does.

## 5. Command execution — **4 PASS · 0 PARTIAL · 0 FAIL, 3 defects fixed**

`scripts/command_execution.py` censuses every process-spawning call site and then
**drives** the ones that take a target with hostile input. Full evidence:
[122](122-command-execution.md).

| Question | Verdict | Executed result |
|---|---|---|
| does any collector input reach a shell? | PASS | **0** `shell=True`/`os.system`/`os.popen`, **0** string command lines; 91 argv-list call sites in 50 modules |
| can hostile input become an argument? | PASS | 3 call sites × 6 hostile inputs each; the drill's own control — a deliberate `shell=True` — is reported as a failure, so the check can fail |
| is `--` passed before every untrusted positional? | PASS | 2 of 91 call sites pass a caller-supplied positional straight into the spawn; both terminate it with `--`, and the one site that builds its argv a function above (`_run` under `_pull_docker`/`_pull_podman`) is read for the same terminator. The population is measured, not assumed: a probe fails if a driven site cannot be mapped |
| privileged surfaces | PASS | 0 docker-socket references, 0 `kubectl exec`, 0 drop-to-root |

**What the drill found, by running it.** There was no shell anywhere, and three
real argument-injection defects anyway:

- `network_scanner/probing/ssh_keyscan.py` passed the target host straight into
  `ssh-keyscan`. A probe with `-oProxyCommand=touch /tmp/canary` put that value in
  argv — and the OpenSSH **client** honours `-oProxyCommand`, i.e. command
  execution. Now grammar-validated (`_HOSTNAME`) with an early `REFUSED` and `--`.
- `worker/workspace/repo_cloner.py` passed a remote URL and a commit into `git`.
  Now `_REMOTE_URL`/`_COMMIT` validated before spawning, `--` in clone and
  checkout, and `ValueError` on refusal.
- `container_scanner/image/puller.py` passed an image reference into
  `docker pull`/`podman pull`. Now `_REFERENCE`-validated with `--` before it.

Legitimate values (`nginx:1.27`, a normal hostname, an `https://` clone URL) still
pass. `systemctl` was already correct: `--` before the unit, plus `O_NOFOLLOW`, an
owner check, ELF magic and a capabilities check on the binary.

**What it does not prove.** The recorder stands in for `subprocess`, so the drill
proves what *would have been* passed to `ssh-keyscan`/`git`/`docker`, not what
those tools did with it. A mounted docker socket or a privileged container is a
deployment fact a source census cannot see.

## 6. SSRF — **6 PASS · 0 PARTIAL · 0 FAIL**

Guide 121 proved the policy half: a CIDR, `127.0.0.1`, `169.254.169.254`, an
off-scope host and a source path outside the declared roots are refused
server-side for the most powerful principal. That leaves the harder question —
what happens *after* a legitimate target is approved. Guide
[125](125-ssrf.md) answers it by executing the four ways around a policy.

| Question | Verdict | Executed result |
|---|---|---|
| is the target authorized server-side? | PASS | 121's target row re-executed here: no scope → 409, `/8` → 422, `127.0.0.1` → 422, metadata IP → 422, off-scope host → 409, `/etc` source → 422 |
| does the runtime egress guard refuse an outbound connection? | PASS | with an empty allowlist, a connection to `169.254.169.254:80` raises `EgressBlocked` **before a socket exists** |
| can an approved name be re-pointed at a private address? | PASS | an allowlisted name is **pinned** at install; re-resolving it to `127.0.0.1` afterwards is refused as DNS rebinding, and a name that never resolved is refused rather than resolved lazily |
| is a redirect to an unapproved destination followed? | PASS | a real 302 is served and followed by `urllib` with no guard (the control), and refused with the guard installed — to a local internal service and to the real metadata address |
| does a hand-built socket bypass the guard? | PASS | `socket.socket().connect()` is wrapped too; a destination outside the allowlist is refused |
| does the guard still allow what it should? | PASS | an allowlisted destination answers 200 with the guard installed and without it |

**Two ways around the guard were found and closed while writing this.** The
allowlist was keyed on the *name* as the caller passed it, so an approved name that
later resolved to loopback was allowed — rebinding. And `socket.create_connection`
is not the only exit: a caller that builds its own socket walked past the guard
entirely. Both are fixed in `api/security/egress_guard.py` (pin at install, connect
to the pinned address, wrap `socket.socket.connect`) and both are now negative
controls: neutralise the guard and the drill's redirect row goes red.

**What it does not cover, stated rather than implied.** UDP/`sendto`, raw sockets
and direct syscalls are outside a Python-level guard; deployment egress policy is
the control there. A collector that shells out (`git`, `ssh`, `docker`) makes its
own connections — guide 122 covers its arguments and deployment policy its traffic.
And the guard is off unless `EGRESS_GUARD=enforce`: this is a deployment property,
proved rather than assumed.

## 7. Multi-tenant isolation — **7 PASS · 1 PARTIAL · 0 FAIL**

The review asked for isolation that is "cryptographically **and** logically"
enforced. Those are two claims, and guide [126](126-tenant-isolation.md) grades
them separately: the logical half is measured by execution against two real
tenants, and the cryptographic half is graded PARTIAL because it is not true.

| Question | Verdict | Executed result |
|---|---|---|
| can tenant A read a row that belongs to tenant B? | PASS | inside A's scope a plain `select` returns only A's rows; B's primary key resolves to `None`; A's own row still resolves (the control that stops this being an empty-result pass) |
| can tenant A write a row into tenant B? | PASS | a new row is stamped with the active tenant; naming B's `tenant_id` from inside A is refused, and nothing persists |
| can tenant A update or delete a row it cannot see? | PASS | a cross-tenant `update` touches **0 rows**, and B's row still reads what it read |
| does a query that forgets the predicate fail closed? | PASS | text SQL and Core selects on a tenant-owned table raise `TenantScopeViolation` inside a scope rather than returning both tenants |
| does a valid session plus a spoofed header buy the other tenant's scope? | PASS | `X-Tenant-ID: <B>` with A's valid session is refused; B's own header resolves B (control); no session resolves nothing |
| is the isolation the filter's doing, or the data's? | PASS | from a platform scope the same query returns **both** tenants' rows — so the separation is the scope, which is exactly what the rows above measure |
| does PostgreSQL enforce the boundary, or only the Python scope? | PASS | migration `0132` puts a **forced** policy on all 157 tenant tables; as a non-owner role, a connection with no tenant setting reads **0** rows, a tenant-A setting reads **1**, the explicit platform wildcard reads **2**, a foreign `INSERT` is refused by the policy and a foreign `UPDATE` touches **0**. The owner control shows why `FORCE` matters: the same owner reads 2 rows without it and 1 with it |
| is the isolation cryptographic? | **PARTIAL** | reading the store file directly returns both tenants' rows in plaintext |

**Why that last row is PARTIAL and not PASS.** One database, one schema, a
`tenant_id` column, an ORM filter and a row-level policy is *enforcement*: it
stops a request, and it now stops a stray connection too — a psql session, a BI
tool, a service that forgot the guard reads nothing at all. It is not *encryption*:
a dump, a backup or a stolen disk still contains every tenant's rows in plaintext,
and a superuser reads across tenants by design (the drill measures that rather
than hiding it). Closing it needs per-tenant keys held by the tenant. A bank
buying a SaaS tenancy should read that sentence rather than a green tick.

## 8. Evidence tampering — **covered**

Guide 112 applies nine tampering attacks to a real stored scan: **8 detected, 1
undetectable by design**. The chain is hash-linked with `previous_hash` and a
manifest anchor; the Twin verifies the chain before projecting, which was the open
path from evidence corruption to Twin corruption. The residual is stated rather
than hidden: the scan manifest is unsigned, so an attacker who rewrites payload,
chain **and** manifest verifies PASS — that needs a signing key or an off-site
anchor, not another check.

## All eight are now answered

Six closed by execution (#1 authentication, #2 authorization, #3 agent identity,
#4 secret management, #5 command execution, #6 SSRF), one by an earlier pass
(#8 evidence tampering, guide 112), and #7 measured with its cryptographic half
recorded as PARTIAL. That last PARTIAL is the one a bank should read: the tenancy
boundary is enforced by code, not by a key.
