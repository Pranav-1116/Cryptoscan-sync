# 119 — Security blockers, graded against execution

A review named eight security properties a bank must be able to test before it
runs this platform. This guide answers the first two by **executing** them, and
records where the other six stand. Nothing here is a plan; every claim below is
regenerated by a script that can produce a different answer tomorrow.

Grades are the same three used everywhere in this series: **PASS** (measured, and
the measurement can fail), **PARTIAL** (measured, with a named property not
exercised), **FAIL** (a probe answered wrong). `UNPROVEN` is never a pass.

## 1. Authentication — **3 PASS · 5 PARTIAL · 0 FAIL**

`scripts/auth_qualification.py` drives the real auth router, the real session
manager and the real user store through the production session gate, over HTTP,
against a temporary database with PBKDF2 hashes at the configured work factor.

| Question | Verdict | What was executed |
|---|---|---|
| login | **PASS** | correct credential mints a token; wrong password, unknown user and empty password all refused; unknown user and wrong password answer **identically** (no enumeration) |
| session / token | **PASS** | token accepted at the gate; tampered payload refused; token signed by another deployment refused; missing and malformed credentials refused; a role header does not change identity; cookie is `HttpOnly` + `SameSite=Lax` |
| MFA | PARTIAL | password alone mints **no** token and returns `mfa_required`; the challenge token is **not** accepted as a session; wrong TOTP refused; correct TOTP mints a session; recovery code works once |
| expiry | PARTIAL | an expired session is refused; a live one is accepted; the token carries an expiry inside the configured window; an MFA challenge is not a session |
| revocation | **PASS** | logout kills the token at the gate; the revocation is **store-backed** (a second client sees it); revoke-all ends other sessions |
| password policy | PARTIAL | short and single-class passwords refused 422; a strong one accepted; the stored credential is `pbkdf2_sha256` and does not contain the plaintext; a plaintext stored secret never verifies in production; public registration cannot ask for a privileged role |
| lockout | PARTIAL | every failure refused; the correct password is refused **while locked**; the lock lives in the users table so a fresh service object still refuses; other accounts unaffected; failures audited |
| credential handling | PARTIAL | the password is never echoed; `/auth/me` carries no hash and no MFA secret; an error body does not repeat the attempted password; a token in the query string grants nothing |

**The five PARTIALs are named, not averaged away.** No external authenticator
(hardware key, IdP push) is exercised — TOTP is the only second factor here. There
is one session TTL, so idle and absolute lifetimes are not distinguished per role.
Password breaches and reuse are not checked. Lockout is per account and per
attempt, not per-source velocity. And log redaction is a separate probe: this row
reads HTTP responses only, not what a logger wrote.

## 2. Authorization — **8 PASS · 1 PARTIAL · 0 FAIL**

`scripts/authorization_boundaries.py` reads the boundary each operation
**declares** from its dependency tree, then sends the request as Admin, Auditor
and Viewer through the real app and compares the two. It executed **1,617
decisions** across **1,225** operations.

| Question | Verdict | Executed result |
|---|---|---|
| are the three roles distinct? | PASS | `admin → superadmin`, `viewer → readonly`, and viewer permissions ⊂ auditor ⊂ admin (strictly) |
| can an **Admin** cross? | PASS | 0 escapes |
| can an **Auditor** cross? | PASS | 0 escapes |
| can a **Viewer** cross? | PASS | 0 escapes |
| declared = enforced? | PASS | 1,617 decisions, **0 violations**, 9 over-tight |
| is it enforced without a session? | PASS | **0 of 562** gated writes answered without a token |
| does a forged token get in? | PASS | **0** writes accepted a token signed by another deployment |
| what declares nothing? | PARTIAL | **180 of 562** gated writes are session-only — reported by area |
| is the *target* authorized server-side? | PASS | no scope fails closed (409); a `/8`, `169.254.169.254` and `127.0.0.1` are refused 422 when saving a scope; a host or CIDR outside the approved scope is refused even for an admin; a source scan of `/etc` is refused |

**The instrument proves it can fail.** The comparator is exercised with a
requirement that forbids a role and a decision that allows it, and it reports the
violation; the same comparator is then used for every decision above.

**Two things the drill learned by doing it, both worth recording.**

- Sweeping every write with an empty body **engaged the platform's emergency
  stop**. The sweep had POSTed to `/network/crypto-stop`, and every later
  collection answered `409 network_observation_stopped` — a drill that changed
  what it measured. Destructive routes are now named and skipped, and the skip is
  printed in the report rather than being invisible.
- A 403 is not automatically a boundary violation. Routes guarded by **tenant
  membership** refuse a platform principal who belongs to no organisation, which
  is the tenancy boundary working. Those routes are counted and excluded from the
  role comparison, and the count is printed.

**What remains open here.** 180 gated writes are callable by any authenticated
principal, including a Viewer. That is a policy question per area — the review's
own framing — not something a drill can grade, and the area breakdown is in the
artifact so a bank can decide.

## 3. Agent machine identity — **open**

The parts exist and the binding does not:

- `api/security/mtls.py` builds a server context that **requires** client
  certificates (`CERT_REQUIRED`, site CA as trust anchor, TLS ≥ 1.2, no
  compression) and refuses to build without the material.
- `api/routers/ingestion.py` already verifies **Ed25519 signatures** over the
  observation document, reports `cryptoscan.authenticity/1`, and has a
  `REQUIRE_SIGNATURES` switch that fails closed.

What is **not** built is the join: the client certificate presented at the TLS
layer is never read by the application, no certificate fingerprint is registered
against an agent identity, and an observation is therefore not bound to the key
that authenticated the transport. So today the chain is *two independent facts* —
"this TLS client had a valid certificate" and "this payload carries a valid
signature" — rather than one identity.

**What closes it.** Agent registration that records the certificate fingerprint
(SPKI hash, not the whole certificate), a middleware that extracts the peer
certificate and refuses a request when the fingerprint does not match the agent
it claims to be, and an observation that must be signed by the same key. Graded
by a drill that runs a real TLS handshake with a matching certificate, a
mismatched certificate and no certificate.

## 4. Secret management — **3 PASS · 2 PARTIAL · 1 FAIL**

`scripts/secret_management.py` puts a distinctive canary through four paths — a
log line, an error response, an access line, the console's storage — and scans
source for credential shapes. Full evidence: [123](123-secret-management.md).

| Question | Verdict | Executed result |
|---|---|---|
| is a credential committed to the tree? | PASS | 0 findings across 7 patterns in product code; **13 allow-listed with a written reason**, and 16 fixture hits in `scripts/` listed separately rather than silently excluded |
| does a secret written to a log come back out? | PARTIAL | a `password`/`api_token`/`private_key` field is masked (and the control proves the canary is visible when redaction is off) — but redaction is **key-based**, so a secret interpolated into the message string is written verbatim |
| can a failing call return a credential to the caller? | PASS | an unhandled driver error carrying `postgresql://svc:<canary>@…` returns a body without it, while a hand-written detail is returned verbatim (the control that proves the check is not passing on empty bodies) |
| does the request log record the credential it was given? | PASS | `Bearer`, `X-API-Key` and cookie canaries absent from the access line |
| does the console keep a session where a script can read it? | **FAIL** | `frontend/src/lib/api.ts` writes the session token to `localStorage["zelinx_token"]` |
| does a credential travel in a query string? | PARTIAL | `/?token=` on the invite page: a one-time `csi_…` invite token, in history and any `Referer` |

**The FAIL is the finding.** The backend already sets an httpOnly
`cryptoscan_session` cookie and the console verifies the session with
`GET /api/v1/auth/me`, so the `localStorage` copy is redundant *and* exposed: any
XSS on the console can read a bearer token. The fix is to hold the token in memory
in `lib/api.ts` and let the cookie carry the session across a reload — a frontend
change across every `getToken()` call site, which is why it is recorded as a FAIL
here rather than quietly patched.

## 5. Command execution — **3 PASS · 1 PARTIAL · 0 FAIL, 3 defects fixed**

`scripts/command_execution.py` censuses every process-spawning call site and then
**drives** the ones that take a target with hostile input. Full evidence:
[122](122-command-execution.md).

| Question | Verdict | Executed result |
|---|---|---|
| does any collector input reach a shell? | PASS | **0** `shell=True`/`os.system`/`os.popen`, **0** string command lines; 91 argv-list call sites in 50 modules |
| can hostile input become an argument? | PASS | 3 call sites × 6 hostile inputs each; the drill's own control — a deliberate `shell=True` — is reported as a failure, so the check can fail |
| is `--` passed before an untrusted positional? | PARTIAL | 3 of 91 call sites take an untrusted positional; all three now pass `--`, the rest have nothing to terminate |
| privileged surfaces | PASS | 0 docker-socket references, 0 `kubectl exec`, 0 drop-to-root |

**What the drill found, by running it.** There was no shell anywhere, and three
real argument-injection defects anyway:

- `network_scanner/probing/ssh_keyscan.py` passed the target host straight into
  `ssh-keyscan`. A probe with `-oProxyCommand=touch /tmp/canary` put that value in
  argv — and the OpenSSH **client** honours `-oProxyCommand`, i.e. command
  execution. Now grammar-validated (`_HOSTNAME`) with an early `REFUSED` and `--`.
- `worker/workspace/repo_cloner.py` passed a remote URL and a commit into `git`.
  Now `_REMOTE_URL`/`_COMMIT` validated before spawning, `--` in clone and
  checkout, and `ValueError` on refusal.
- `container_scanner/image/puller.py` passed an image reference into
  `docker pull`/`podman pull`. Now `_REFERENCE`-validated with `--` before it.

Legitimate values (`nginx:1.27`, a normal hostname, an `https://` clone URL) still
pass. `systemctl` was already correct: `--` before the unit, plus `O_NOFOLLOW`, an
owner check, ELF magic and a capabilities check on the binary.

**What it does not prove.** The recorder stands in for `subprocess`, so the drill
proves what *would have been* passed to `ssh-keyscan`/`git`/`docker`, not what
those tools did with it. A mounted docker socket or a privileged container is a
deployment fact a source census cannot see.

## 6. SSRF — **partially covered**

Guide 121's target-authorization row already refuses, server-side and for the most
powerful principal: a CIDR, `127.0.0.1`, `169.254.169.254`, a host outside the
approved scope, and a source path outside the declared roots. Still open: HTTP
redirect following, DNS rebinding (a name that resolves to a private address after
the check), and non-HTTP collectors that take a URL. The egress guard
(`api/security/egress_guard.py`) is the runtime half and needs a drill that turns
it on and proves a disallowed connection is refused.

## 7. Multi-tenant isolation — **open**

The machinery exists — `db/tenancy.py`, `TenantScopeMiddleware`, tenant-role
guards, and a tenant guard that stamps `tenant_id` on writes. The drill to build:
two tenants, every read and every write, cross-tenant attempts with a
**valid** session for the other tenant, with a spoofed `X-Tenant-ID`, with a
crafted `tenant_id` in the body, and at rest (does a query without a tenant
predicate return rows from both?). Isolation has to be *cryptographic and
logical*: the plan is to prove the logical half by execution and state plainly
that a shared database is not cryptographic isolation.

## 8. Evidence tampering — **covered**

Guide 112 applies nine tampering attacks to a real stored scan: **8 detected, 1
undetectable by design**. The chain is hash-linked with `previous_hash` and a
manifest anchor; the Twin verifies the chain before projecting, which was the open
path from evidence corruption to Twin corruption. The residual is stated rather
than hidden: the scan manifest is unsigned, so an attacker who rewrites payload,
chain **and** manifest verifies PASS — that needs a signing key or an off-site
anchor, not another check.

## The order I would take the remaining four

Command execution (#5) was taken before secret management (#4) because it is the
higher-severity of the two for an active scanner; both are now measured, #4 with
one open FAIL.

1. **Agent identity (#3)** — the pieces are there; the binding is a middleware and
   a registration record.
2. **SSRF (#6)** — extend 121's target row with redirects, DNS rebinding and the
   egress guard.
3. **Tenant isolation (#7)** — two tenants, every route, both directions.
4. **The console's `localStorage` token** — from #4: move the token to memory and
   let the httpOnly cookie carry the session.
