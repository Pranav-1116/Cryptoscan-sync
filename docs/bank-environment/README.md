> [Hardware discovery](128-hardware-discovery.md) (**7 pass · 0 partial · 0 fail**)
> answers the review that opened with one rule: hardware is not a scanner that
> emits an HBOM. The HSM observation now carries cluster, HA state, partitions,
> algorithm capabilities and PQC (ML-KEM/ML-DSA) — metadata only, and the guard
> that refuses key material raises instead of asserting, so `python -O` no longer
> deletes it. A hardware relationship without an evidence record is refused
> (`UnevidencedRelationship`), drift names firmware, crypto capability and PQC as
> separate events, and a synthetic 600-asset estate projects in 0.02 s. This
> pass also added the reader those collectors were missing — `hardware/host/linux.py`
> takes DMI, memory, disks, SMART health, PCI and NICs from a sysfs tree and five
> allowlisted binaries, with `shell=False`, validated device nodes and an argv
> allowlist that refuses a shell string; a refused command, an unprivileged host
> and a missing binary are each proven to degrade to a stated reason rather than
> a crash.
>
> The same pass closed the network half: `hardware/host/snmp_bridge.py` carries
> the network scanner's SNMPv2c client into the estate, and the client now walks
> **ENTITY-MIB** — which is where a switch actually keeps its serial, model and
> firmware, rather than a marketing sentence in sysDescr. A switch arrives as a
> canonical observation (Cisco C9300-48P, serial `FDO2140A1B2`, firmware
> `17.9.4a`, TLS-termination seam) with the community string used and dropped:
> the bridge refuses to return a payload that echoes it.
>
> The appliances that do not answer SNMP are covered too:
> `hardware/host/netconf.py` negotiates a NETCONF session and reads
> `ietf-system`/`ietf-hardware` with a read-only `<get>` — there is no
> `edit-config` path in the module to misuse — and `hardware/host/restconf.py`
> reads the same YANG models over HTTPS, refusing a cleartext device URL. All
> three transports produce one `NetworkDeviceFacts` and one observation
> projection, so the estate cannot end up with three versions of the same
> switch, and each refuses a device that echoes the credential in a field it
> carries.
>
> The security hardware got the same treatment: `hardware/hsm_readers/pkcs11.py`
> reads a partition's `CK_TOKEN_INFO` and its mechanism list — firmware, serial,
> model, login and write-protection flags, and the post-quantum mechanisms an
> appliance advertises (`CKM_ML_KEM`, `CKM_ML_DSA`, `CKM_SLH_DSA`) — with the
> PIN in the child's environment and never in argv, where `ps` would show it to
> every user on the host; an argv carrying `--pin` is refused before anything is
> spawned. `hardware/hsm_readers/kmip_query.py` asks the appliance what it can
> do over KMIP `Query` — vendor identification, supported operations, object
> types, profiles — and can build that one operation and nothing else. Both feed
> the existing `HsmHardwareScanner`, so the estate keeps one HSM observation and
> not one per protocol.
>
> Correlation now covers network hardware as well as applications:
> `hardware/network_correlation.py` turns a TLS observation from a device into an
> evidenced `TERMINATES_TLS` edge (certificate → load balancer), folds the same
> device's configuration in — a trustpoint, an `ssl certificate` line, a PKCS#11
> token — and produces `lb-01 -USES_HSM-> HSM-01` on config evidence. Because the
> certificate is the edge subject, an HA pair presenting one certificate is
> visible as shared, and blast radius lists the certificates at risk beside the
> applications instead of counting a certificate as an application (which it did,
> until this pass).
>
> Drift now answers the change-board question too: `hardware/change_correlation.py`
> puts a hardware change beside the certificate, application and policy records
> that moved in the same window, and labels the result `CORRELATED`, `PARTIAL`,
> `UNACCOMPANIED`, `ISOLATED` or `SUSPICIOUS` — the last being a certificate that
> moved while the appliance holding its key did not. `migration_readiness` states
> the PQC finding without flattering it: an ML-DSA capability that arrived with
> no application or certificate movement is "an available migration, not a
> completed one". Every result carries its own disclaimer that proximity is not
> causation, and nothing here mints an edge — an edge needs evidence naming both
> ends, which a timestamp is not.
>
> That correlation is wired into the live pipeline, not left as a library the SOC
> would have to remember to call: `hardware/live/change_feed.py` turns every drift
> row into a live hardware event, feeds it through `LiveHardwareController.ingest`
> so it lands in the timeline, the evidence chain and the next HBOM version, and
> returns the correlation verdict in the same response that carried the event. The
> canonical taxonomy has no PQC event type, so post-quantum rows ride
> `CRYPTO_CAPABILITY_CHANGED` with `payload["pqc"]` rather than inventing a type
> the state engine would accept and then ignore; a drift row the mapping does not
> know is emitted as `HARDWARE_CHANGED` with its original type in the payload
> instead of vanishing. A change crossing the feed/controller seam twice is
> counted once — a correlation count that double-counts its own input is worse
> than no count.
>
> The two gaps that were probes are now readers, built the same way the Linux
> one was. `hardware/host/windows.py` reaches Windows through `Get-CimInstance`
> over a **frozen table of eight CIM classes**, each asked for named properties
> only — no parameter of the module accepts a query, a class name or a script, so
> a caller cannot turn the reader into a shell, and a class outside the table
> (`Win32_Process`) is refused rather than run. It reads platform identity, BIOS
> version and release date, per-disk firmware, processor and memory, `Win32_Tpm`
> metadata and the Device Guard state; the TPM capabilities WMI does not expose
> are left absent rather than invented. It is executed here against a recorded
> CIM transcript, because no Windows host exists on this runner — which is the
> one thing it cannot prove, and the artifact says so.
>
> `hardware/hsm_readers/rest.py` reads an appliance whose only surface is the
> vendor's own HTTPS API, under a rule that keeps it honest: **an endpoint exists
> only because a published vendor document says so**. Every
> `DocumentedEndpoint` carries the page URL it was read from and the fact that
> page says it returns; every shipped endpoint is a `GET`; parameters are encoded
> as single path segments, so a serial number cannot walk into
> `/actions/zeroize`; and the reply is projected down to metadata, so a wrapped
> key in a response yields nothing and a secret in a projected field stops the
> read. The Thales Luna manifest is written from the REST API reference (7.x) and
> exercised against replies shaped like its own examples. Utimaco, Entrust
> nShield and Fortanix DSM are named in the module as **undocumented** — asking
> for one raises, with the reason — because inventing `/api/v1/...` for them
> would produce a reader that returns an empty observation and calls it success.
> A partition list is deliberately not parsed: the guide does not pin that shape,
> so partition ids come from the operator's inventory.

> [Hardware breadth, usage and impact](129-hardware-breadth-and-impact.md)
> (**6 pass · 0 partial · 0 fail**) answers the sharper follow-up: *host
> collection is not a complete hardware scanner*. `hardware/components.py` reports
> all fifteen component classes a bank audits — CPU, memory, motherboard, BIOS,
> firmware, PCI, GPU, NIC, storage controller, disk, RAID, TPM, HSM, smart card,
> crypto accelerator — and gives each one **three** possible answers rather than
> two: `PRESENT`, `ABSENT` (the reader looked and there is none) and `UNKNOWN`
> (nobody looked, and here is why). That third state is the whole point: an
> unprivileged collector that reports "no GPU, no TPM, no accelerator" is lying by
> omission, and this one cannot. The Linux reader gained `lscpu` so the processor
> is a fact rather than a gap, and PCI class codes identify the GPU, RAID
> controller and crypto accelerator; `tpm2_getcap` and `opensc-tool` closed the TPM
> and smart-card classes, behind a **per-argument** allowlist so that an
> allowlisted binary cannot be asked for a second subcommand it happens to
> support. On Windows the reader now reads twelve CIM classes: `Win32_PnPEntity`,
> `Win32_VideoController`, `Win32_NetworkAdapter` and `Win32_PhysicalMemory` name
> the PCI devices, the display controller, the adapters and the memory modules
> socket by socket, so only RAID and a crypto accelerator remain `UNKNOWN` — the
> two things Windows gives no class for — and each says why rather than reading as
> an empty server.
>
> `hardware/usage_graph.py` draws `HSM-01 —USED_BY→ Payment API` only where a
> configuration names both ends — the PKCS#11 token label, the KMIP server — and
> records the file and block as the evidence. A label no discovered appliance
> carries is `UNRESOLVED` (a dependency on something the estate has not found is
> worth knowing); a label two appliances claim is `AMBIGUOUS` and refused, with
> both candidates named, because picking one would be a guess wearing an evidence
> id. Capability is `SUPPORTS` — a link between an appliance and an algorithm,
> modelled separately so blast radius never counts `RSA-3072` as a device.
> `hardware/business_impact.py` walks the chain the review drew, hardware →
> application → service → business system, and prints the sentence an operator
> reads at 03:00: *"HSM-01 failure reaches 2 application(s); 1 service(s); 1
> critical business system(s) (Card Authorization)"* — with applications that have
> no business mapping **named** rather than counted as zero.
>
> Running the collection guards rather than describing them found two real
> defects: an HSM payload carrying a PEM block was accepted because the guard only
> knew the `private_key` spelling, and the controller recorded a PQC change under
> its canonical event name, so the same change crossed the feed/controller seam
> twice and inflated the correlation counts. Both are fixed, and both are now
> probes. The Windows device-tree work was verified the same way — the transcript
> is the reader's own input, and the projection's answer is what the artifact
> prints, not what a paragraph claims.
>
> The artifact closes with the review's reclassification table, and the ratings
> are **computed, not typed**: each area names the row that proves it plus a
> ceiling, so a green area whose probe fails degrades in the same run — and a
> probe forces one row to `FAIL` to prove the downgrade actually happens. The
> result is 3 green (Linux collection security, Linux evidence model, Linux host
> collector as a foundation), 9 amber, 0 orange, 0 red: physical hardware breadth,
> HSM, hardware relationships and hardware drift all move off 🟠, and security
> moves from a 🔴 broad concern to 🟡 **qualification still required** — the
> guards refuse rather than assert, and what is left is a bank Linux host, a
> Windows runner and the two readers named above.

> [Vendor evidence](130-vendor-evidence-and-vbom.md)
> (**9 pass · 0 partial · 0 fail**) answers the follow-up that matters more than
> any of it: *a vendor declaration is not a verified deployment*. The VBOM's
> dangerous shortcut is one sentence long — the vendor says product X supports
> ML-DSA, therefore the payment system uses ML-DSA — and
> `vendor_intel/vendor_evidence.py` refuses it in three places. **A capability is
> not a usage**: `CAPABILITY_DECLARED`, `CAPABILITY_OBSERVED` and `USAGE_OBSERVED`
> are three events over eight evidence types (`DECLARED`, `IMPORTED`,
> `CONFIGURED`, `OBSERVED`, `RUNTIME_OBSERVED`, `NETWORK_OBSERVED`, `INFERRED`,
> `UNKNOWN`), and there is no path from the first to the third except through the
> second. **A declaration has a version and the bank has another**: a crypto
> profile written for firmware 8.2.1 does not describe an 8.4.0 appliance, and the
> verdict — `MATCHED`, `PARTIAL_MATCH`, `VERSION_MISMATCH`, `PRODUCT_MISMATCH`,
> `DEPLOYMENT_UNVERIFIED`, `EXPIRED`, `SUPERSEDED`, `UNKNOWN` — withholds the
> declared capabilities when it is not `MATCHED`/`PARTIAL_MATCH`. A probe replaces
> the gate with a constant `MATCHED` to prove the refusal is the gate and not a
> sentence in the guide.
>
> **Sources disagree, and the disagreement is the finding.** Vendor 3.0.13, SBOM
> 3.0.11, runtime 3.0.11 is a `CONFLICT` with all three rows kept — never a
> "latest" value; a second probe shows the CBOM's `AES-256` capability and the
> runtime's `AES-128-GCM` surviving side by side rather than being collapsed. Each
> capability row carries eighteen fields including its applicability verdict and
> six separate flags (`vendor_declared`, `bank_observed`, `runtime_observed`,
> `production_usage`, `version_matched`, `evidence_fresh`), so a UI shows "vendor
> declared ✓ / bank observed ✓ / runtime observed ?" instead of one boolean. Due
> diligence is a 22-section record whose gaps are named rather than scored as
> zero; freshness turns a 2024 questionnaire into `VENDOR_EVIDENCE_STALE` with its
> age; lifecycle dates override a stale `SUPPORTED` label; and the vendor→product→
> appliance→application→critical-system chain and the vendor→SDK→container chain
> answer "which bank systems depend on Vendor-X's HSM?" and "what breaks if SDK
> 4.2 goes EOL?" with per-level counts. The risk rating is a list of weighted,
> reasoned factors — a probe asserts two runs with the same inputs are identical,
> so a rating can be reproduced in front of a regulator.

> [Second pass](131-vendor-evidence-deep.md) (**7 pass · 0 partial · 0 fail**) then
> closes the five gaps that artifact named against itself, because a list of what
> is missing is only useful if somebody works through it. **Vendor paperwork is
> read, not fabricated**: a questionnaire — text, Markdown table, or the text layer
> of a PDF — is parsed field by field, each value citing the line it came from and
> that line's hash; an encrypted file, a scanned page or a document with no vendor
> is refused with a reason instead of yielding an empty declaration, and everything
> extracted is `IMPORTED` and `requires_review`. **Identity has two axes**:
> `crypto_profile_version` sits beside the firmware version, so a document written
> against crypto profile 3.0 is `VERSION_MISMATCH` on an appliance running 3.1 even
> when both report firmware 8.4.0 — and a profile the deployment never reports
> leaves the answer `PARTIAL_MATCH`, not `MATCHED`. **Algorithm names are resolved,
> not compared as strings**: `AES256`, `aes_256` and `AES-256` are one identity,
> `AES-256` against `AES-256-GCM` is `PARTIAL` because one source says less, and
> `AES-128` against `AES-256` is a `CONFLICT` with the size named; a name outside
> the alias table is carried verbatim and flagged, never guessed. **`USAGE_OBSERVED`
> is evidence**: a metadata-only session transcript is decoded into primitives —
> `TLS_AES_256_GCM_SHA384` into `AES-256-GCM` and `SHA-384`, a hybrid
> `x25519mlkem768` group into `X25519` plus `ML-KEM-768`, which is post-quantum key
> establishment observed rather than declared — with one citation per session, a
> record carrying `payload` or `premaster_secret` refused by name, and an
> undecodable suite reported instead of guessed. **Vendor→vendor edges exist**:
> a sub-vendor chain with depth, path and evidence, cycles refused rather than
> followed, and the estate reached through an embedded vendor counted apart from
> the estate bought directly. Two further rows make the evidence reach the
> document: the existing `VbomGenerator` now accepts the evidence-bearing rows, and
> `pqc_coverage` is printed beside `pqc_evidence_backed` so a post-quantum tick
> cannot be quoted without saying whether a session backs it. Every `PARTIAL` is
> enumerated in a ledger that cannot render it as a pass, and `--check` exits
> non-zero on a partial as well as on a failure.

> [The evidence pipeline](132-vendor-evidence-pipeline.md) (**6 pass · 0 partial ·
> 0 fail**) is the part a bank actually runs: its own logs, its own register, and
> a row somebody can defend. **The logs it already keeps**: a Zeek `ssl.log`
> (`#fields` header, tabs, `-` for absent), a CSV export (mapped through an alias
> table, unknown columns named) and an access log with `$ssl_cipher` appended are
> read into session records — a file with a `premaster_secret` column is refused
> outright, a row without a cipher is counted with its reason, and a file that
> yields no session raises instead of reporting calm. **Which workload used it**:
> peers join a register, so one endpoint and one application is `ATTRIBUTED` with
> its CMDB citation, a shared appliance hosting two applications is `AMBIGUOUS`
> with both named and neither chosen, an endpoint with no application is
> `PARTIAL`, and an unregistered peer is `UNATTRIBUTED` — it keeps the
> collector's asset and gains no application. The workload table prints its
> coverage (57.1%) and keeps the remainder as an unknown workload rather than
> spreading it over the applications that were identified. **Sub-vendors from the
> SBOM**: a CycloneDX `supplier` (then `publisher`, then `group`, and never the
> component's name) becomes an edge cited to `sbom:<serial>#<bom-ref>`; a
> component with no supplier is listed, a component supplied by the parent is a
> self-edge, and a duplicate is counted. **The bank's own spellings**: an alias
> table may add `AESGCM256 -> AES-256-GCM` but may not redefine `AES256`, may not
> point at a name nobody knows, and emits its review stub unfilled so that
> signing an empty value is visible. **A section can be filled in and support
> nothing**: the twenty-two-section completeness check says `COMPLETE` while the
> evidence audit says 0 of 22 sections are supported — both numbers are printed,
> and a citation that does not resolve in the evidence index is `UNRESOLVED`, not
> support. The last row follows one log line through decode, attribution, claim,
> VBOM row and coverage statement, so "1 post-quantum tick is evidence-backed" can
> be traced back to `session:C0` in `ssl.log`.

> [SBOM evidence and parser qualification](133-sbom-evidence-and-qualification.md)
> (**10 pass · 0 partial · 0 fail**, 65 probes over a **15 of 15** parser
> matrix) starts from the review beside it
> ([133-sbom-review-as-received.md](133-sbom-review-as-received.md)) and answers
> it by running the parsers rather than describing them — which immediately
> turned up three defects: a `.csproj` parser keyed by a name no filename could
> match (so a `.NET` project produced a *valid-looking empty SBOM*), an npm range
> silently coerced to a pinned version (`^5.0.0` read as `5.0.0`, exactly the
> range/pin confusion the review says must stay visible), and `pyproject.toml` /
> `Pipfile` never read as manifests at all (so a Poetry project with no lockfile
> looked like a project with no dependencies). **Deployed is not described**: a
> registry reference must be digest-pinned — `:latest` is refused, not flagged —
> and a component is `PRESENT_IN_DEPLOYMENT` only when a deployment observation
> cites that digest, otherwise `PRESENT_IN_ARTIFACT`, `PRESENT_IN_SBOM_ONLY` or
> `NOT_IN_SBOM`. **The chain is graded end to end**: commit → build → digest →
> SBOM → deployment, with every missing link named, a backdated SBOM refused and
> a build without an observation explicitly stopping at the artifact.
> **Production evidence cannot degrade to a temporary directory**: no store,
> no backup, no retention or no integrity is `REFUSE`, and ephemeral storage is
> allowed only for dev/test/CI. **Integrity, authenticity and non-repudiation are
> three claims**: SHA-256 earns the first, HMAC the first two, an anchored
> Ed25519 key all three — a revoked key invalidates what it signed, and rotation
> keeps an old signature valid while saying so. **"0 vulnerabilities" is never
> the same answer as "nobody looked"**: six states, so a clean result from a
> stale feed is `STALE_FEED` and an identifier-less component is
> `INSUFFICIENT_IDENTIFIER`. VEX statements expire and must name a reviewer and
> evidence; a detected licence is never an approval; SBOM→CBOM is a four-rung
> ladder (capability → static → runtime → network) that cannot skip; a diff's
> crypto impact is `UNKNOWN` until something observed it; an imported SBOM may
> not overwrite an observed fact; and a hostile document hits a byte/component/
> depth/cycle budget before it hits the CPU. Everything not proven is listed in
> the guide, in the review's order.

> [Enforced where the code runs](134-sbom-enforcement.md) (**8 pass · 0 partial ·
> 0 fail**, 39 probes) is the follow-up a reviewer asks next: *is any of that on
> the path the product takes?* Five gaps closed by enforcement rather than
> documentation. **The artifact store no longer degrades to `/tmp`**: production
> with no configured store, no backup target (`SBOM_STORAGE_BACKUP_DIR`), no
> retention (`SBOM_RETENTION_DAYS`) or no verified integrity raises
> `StorageRefused` naming what is missing, the integrity claim is a real write/
> read/hash round-trip, and the manifest records where the evidence went and
> whether that store was allowed to be ephemeral — the API answers 503 instead
> of writing evidence to a directory that dies with the container. **The parser
> budget is on the scan**: an 80-deep graph withholds the edges and keeps the
> inventory, a cycle breaks exactly one back edge rather than recursing, and
> `parser_budget` travels into the response and the stored manifest. **An

> [IPsec negotiates twice, and PFS is not the DH group in phase 1](162-ipsec-crypto-depth.md)
> (**6 pass · 0 partial · 0 fail**, 30 probes) closes NBOM review item 14. A tunnel has
> **two security associations** — an IKE SA (phase 1: encryption, PRF/integrity, DH
> group) and a CHILD SA (phase 2: ESP encryption, ESP integrity, PFS group) — and
> `cbom.ipsec_crypto` records both rather than one "VPN cipher". The distinction that
> matters in practice is the last column: a CHILD SA with **no PFS group** derives its
> keys from the IKE SA, so one compromised peer key exposes every rekeyed tunnel back to
> the start, and `AES-256 / SHA-256 / DH14` looks strong while having no forward secrecy
> for data. PFS is therefore its own field, never inferred from the phase-1 group, and a
> weak PFS group (DH2, 1024-bit) is judged on its own. Three VPN-specific traps are
> modelled: **IKEv1 aggressive mode with a pre-shared key** sends a hash of the PSK that
> can be attacked offline (not a finding under IKEv2, which has no such mode, and an
> IKEv2 record claiming it is normalised); **`ENCR_NULL`** is reported as
> `NO_CONFIDENTIALITY` — legitimate on a private circuit, not over the internet — and
> never called safe; and a tunnel with **only phase 1** is `NO_CHILD_SA`, because one SA
> is not a tunnel. The estate names every weak transform in use, every peer without
> forward secrecy and every IKEv1 peer, and a document that is not an IPsec estate is
> refused rather than converted. `to_algorithms()` emits
> `KEY_EXCHANGE`/`PRF_AND_INTEGRITY`/`BULK` facts carrying their phase and group size;
> quantum exposure names DH groups and not AES. `POST /cbom/ipsec` exposes it, typed,

> [Network crypto correlation: several changes, one pattern, no verdict](157-network-correlation.md)
> (**5 pass · 0 partial · 0 fail**, 27 probes) closes NBOM review item 19, which asks for

> `CERTIFICATE_MUTATION`, `TRUST_PATH_CHANGE`, `NEW_ENDPOINT`/`ENDPOINT_LOST`,

> [Network asset identity: an address is an attribute, not a name](156-network-identity.md)
> (**5 pass · 0 partial · 0 fail**, 31 probes) closes NBOM review item 20, which is one
> sentence long and entirely right: *not* `IP:port`, because IPs change. An inventory
> keyed on `10.20.1.10:443` rebuilds the estate on every failover — history lost,
> assets invented, findings orphaned. `cbom.network_identity` derives the identity from
> what survives an address change, in a stated order — `asset_id` (CMDB, kept
> verbatim) → `device_id` → `hostname` + environment + location (deterministic
> `NET-XXXXXXXXXX`) → certificate fingerprint → service identity — and **refuses** an
> observation whose only handle is an address and a port, because an identity the
> collector invents is exactly the inventory the review rejects. Address churn becomes
> **history on the asset**: `IP_ADDED`/`IP_REMOVED` with first and last seen per
> address, `multiple_addresses` for a multi-homed device, and `identity_stable` on the
> churn report, so a failover is two attribute changes and not a retirement plus an
> arrival. Two collectors that see one hostname produce one asset with two evidence
> ids and an observation count — and when they disagree about the device type, the
> disagreement is kept as a `conflicts` entry instead of one answer being chosen. A
> disappearance is `ASSET_RETIRED` with the sentence that retirement and a discovery
> gap are indistinguishable. And `link()` names an application only from a declared
> mapping **with an evidence id**; a hostname that looks like an application, a zone or
> a certificate never becomes one, so the load balancer stays an interface fact.
> `resolve()` is the seam to guide 148: a hop asset is attached to an identity only
> when the interface name matches a hostname, SNI or service identity, and an
> unmatched interface stays `UNRESOLVED` rather than being given a name.
> `POST /cbom/network-identity` exposes it, typed, behind the reader roles.

> [NBOM history: what changed, and what moved the wrong way](155-nbom-history.md)
> (**5 pass · 0 partial · 0 fail**, 31 probes) closes NBOM review items 18 and 21,

> [Supported, configured, negotiated: three states, three evidences](154-nbom-tls-states.md)
> (**5 pass · 0 partial · 0 fail**, 27 probes) closes NBOM review item 7, which is a
> data-model complaint and a correct one: `TLS 1.2 supported` is not `TLS 1.2 in
> use`, and `TLS 1.3 negotiated` does not prove it is the only supported protocol —
> the NBOM only ever recorded the third. `cbom.tls_state` keeps **three evidence sets
> per endpoint**, each with its own evidence ids: `SUPPORTED` (what the endpoint
> offered when asked), `CONFIGURED` (what policy says it should do) and `NEGOTIATED`
> (what one handshake produced), with `ADVERTISED`/`ENABLED`/`SELECTED` accepted as
> aliases so SSH and IKE fit the same vocabulary. A fact whose state is unknown, or
> that carries no evidence id, is **refused** rather than sorted into a convenient
> bucket. Two conclusions get explicit gates: *a protocol is disabled* is
> `DISABLED_PROVEN` only from a **complete** authorized enumeration in which it is
> absent (`NOT_ENUMERATED` for a modern handshake, `ENUMERATION_INCOMPLETE` for a
> partial one, because the ClientHellos that never ran are exactly where the old
> protocol hides), and *the minimum version* is claimed from `CONFIGURED` first, a
> complete enumeration second, and **never** from `NEGOTIATED` — the endpoint may
> simply have agreed to what this client offered. In the document the states become
> separate `cryptoscan:supported_*` / `configured_*` / `negotiated_*` properties, so
> no reader can pick up one `tls_version` and guess which of the three it is.
> `POST /cbom/tls-state` exposes it, typed, behind the reader roles.

> [NBOM coverage: an observed endpoint is not the network](153-nbom-coverage-matrix.md)
> (**5 pass · 0 partial · 0 fail**, 29 probes) closes NBOM review items 4 and 5, the
> review's "critical" one: 10,000 endpoints, 6,500 observed must not produce a
> document that reads as the bank's network. `cbom.nbom_coverage` is the coverage
> model — one row per target group with `expected · attempted · observed · failed ·
> unauthorized · excluded`, the derived `unattempted` and `coverage_pct`, and five
> statuses because "not complete" is too coarse to act on: `COMPLETE`, `PARTIAL`,
> `FAILED` (probes ran, none negotiated: a scan failure, not an empty network),
> `UNAUTHORIZED` (nothing attempted: an authorization gap), `UNMEASURED` (no target
> list, where 0% and 100% are both wrong). The review's own numbers produce exactly
> **65.0%, PARTIAL, 1,500 never attempted, basis FLOOR**; `TOTAL` becomes available
> only when every group is `COMPLETE`. The arithmetic is checked rather than clamped —
> an observation above the target count means the target list is stale and is refused,
> as is a probe against an endpoint nobody inventoried. `from_probes` turns the stored
> probe ledger into a row: `OK/TLS_OK` observes, `TIMEOUT/REFUSED/ERROR` fails (never
> plaintext, never healthy), `UNAUTHORIZED` is an authorization gap, and any
> undocumented status is **refused** instead of bucketed — a declared endpoint no probe
> touched becomes `unattempted`, which is exactly the gap a bare probe count hides.
> `attach` writes the block into the NBOM's `metadata.properties`
> (`cryptoscan:network_coverage*`, including `network_may_report_total`), and
> `qualify` reports an NBOM with components and no coverage block as `UNQUALIFIED`
> rather than assumed complete. The review itself is saved at
> `nbom-review-2026-11-02.md`, with an ownership table for the remaining items.
> `POST /cbom/nbom/coverage` and `/nbom/coverage/from-probes` expose it, typed.

> [CBOM → digital twin: one graph, three consumers](152-cbom-digital-twin.md)
> (**5 pass · 0 partial · 0 fail**, 30 probes) closes review item 20's architecture:
> SBOM · STATIC · NETWORK · RUNTIME · HSM/KMS → crypto graph → CBOM → digital twin →
> drift · PQC migration · threat intelligence. `cbom.digital_twin` **projects** the
> twin from guide 147's estate chain, so the twin and the document cannot disagree;
> what it adds is the questions a document cannot answer. A node carries the evidence
> classes behind it and a `claim_level` from one table (`CAPABILITY` < `IMPORTED` <
> `CONFIGURED` < `STATIC` < `NETWORK` < `RUNTIME`), and a library stays `CAPABILITY`
> even when the same algorithm is observed at runtime somewhere else. Every edge keeps
> its evidence ids, no edge dangles — an algorithm only a key or a suite mentions still
> becomes a node, as a capability — and a conflict between two observers survives as an
> edge while a declaration against an observation is resolved by precedence. The three
> consumers answer and never upgrade: **drift** reports `UNEXPECTED_USE`,
> `PARAMETER_DRIFT`, `PARAMETER_UNKNOWN` (policy names a size, nothing recorded one, so
> drift is not asserted), `UNATTRIBUTED`, and `POLICY_NOT_OBSERVED` — the last
> explicitly *not* evidence of absence; **PQC migration** queues only what is in use,
> inherits the node's level, and every verdict names its `REGISTRY_*` basis, so a
> capability-only estate never leads with `IMMEDIATE`; **threat intelligence** matches
> advisories by component and version and keeps exposures apart — `EXECUTING` (a
> process loaded it), `PRESENT` (installed, nothing says loaded), `VERSION_UNKNOWN`
> (neither confirmed nor cleared), `NOT_PRESENT`. `claim_check` re-reads every consumer
> row against its node and fails if one claimed more. `POST /cbom/twin` exposes it,
> typed, behind the same reader roles.

> [Adversarial CBOM: the five blockers, attacked](151-cbom-adversarial.md)
> (**5 pass · 0 partial · 0 fail**, 30 probes) closes review item 21 by attacking it.
> Five red blockers — evidence spoofing, false attribution, weak evidence promotion,
> secret leakage, signature/hash confusion — each handed the most convenient possible
> input, with the pipeline required not to believe it. **One was a real hole**: an event

> [Component completeness: unmeasured is not clean](150-cbom-inventory-completeness.md)
> (**4 pass · 0 partial · 0 fail**, 22 probes) closes the other half of review items 18
> and 19 at the level a CBOM is actually assembled: the **component**, not the system.
> ``cbom.inventory_completeness`` asks three questions per component — was it inspected
> at all, did every task that ran finish, do the tasks agree — and returns
> `UNMEASURED` (nobody looked: the absence of findings is not evidence of absence),
> `INCOMPLETE` (one task stopped early, whatever the finished ones found), `EMPTY`
> (every task finished and found nothing, which *is* a measurement) or `CONTRADICTED`
> (one tool reported clean while another reported a finding — both evidence ids kept,
> never a majority vote). A claim from a task that never finished is a **candidate**,
> not a finding; a claim naming a task that never ran, carrying no evidence id, or
> naming no task at all is **refused**. Only `COMPLETE` and measured `EMPTY` components
> may be counted, so `inventory()` derives `may_report_total` from the rows instead of
> asserting it. The estate chain reports the same block for an estate's inspection
> records, and `POST /cbom/completeness` exposes it, typed, behind the reader roles.

> [TLS termination paths: three relationships, never one attribute](149-cbom-termination-paths.md)
> (**5 pass · 0 partial · 0 fail**, 32 probes) closes review item 9.
> `Client --TLS1.3 AES-256-GCM--> External LB --TLS1.2 AES-128-GCM--> API Gateway
> --TLS1.3 AES-256-GCM--> Payments API` is **three** cryptographic relationships, and
> the middle hop is weaker than both ends. `cbom.termination_paths` chains the hops
> (a hop that connects to nothing is a **gap**, not a one-hop path), keeps one
> relationship per hop with its own version, suite, algorithms and evidence, and
> names the change between adjacent hops — a `TLS_VERSION_DOWNGRADE`, a
> `BULK_CIPHER_CHANGED`, or a `SUITE_CHANGED` at the same version. Versions are
> compared by bulk cipher, because a TLS 1.3 suite names two algorithms and a TLS
> 1.2 suite four; comparing whole suites would report a change on every hop. The
> naive merge is computed **and refused**: `merged_claim` shows the union a careless
> tool would assert and says it "describes no hop". Components are emitted per
> (path, hop, algorithm) so `path:1#hop:2#AES-128-GCM` cannot be read as the
> application's algorithm; edges are hop-scoped (`hop:A→B NEGOTIATES algorithm:X`,
> plus `PRECEDES` for order) and never start at an application or a system, and a
> tunnelling middlebox is `PASSES_THROUGH` rather than a terminator. The estate
> chain builds the same path from the same hops. `POST /cbom/termination-paths`
> exposes it, typed, behind the same reader roles.

> [Network crypto assets: the interface owns the hop](148-cbom-network-assets.md)

> [The whole chain over one estate: seven seams, seven checks](147-cbom-estate-chain.md)
> (**6 pass · 0 partial · 0 fail**, 37 probes) is the increment that stops proving
> layers one at a time. `cbom.estate_chain.run` runs the runtime tracer, the KMS

> [Process-level runtime tracing: the chain is the evidence](146-cbom-process-tracing.md)
> (**5 pass · 0 partial · 0 fail**, 24 probes) closes review item 7 — the gap the
> review calls the biggest one. `cbom.process_tracing` keeps the whole chain:
> application → PID → provider (with version) → operation → algorithm →
> parameters → timestamp → evidence id. A row missing any link is **refused**, not
> promoted, because a partial chain is a claim. The provider version is data: a

> [Coverage in the CBOM, and what an empty CBOM actually says](145-cbom-coverage-render.md)

> [PQC readiness is not the CBOM, and a boolean is not a status](144-cbom-pqc-handoff.md)
> (**5 pass · 0 partial · 0 fail**, 24 probes) closes review items 14 and 15.
> `quantumVulnerable: true|false|null` failed three ways: it said `false` for
> AES-256 without noting Grover, it could not express hybrid or transitional
> states, and it put a **decision** in a document that only ever observed an
> **algorithm**. `cbom.pqc_handoff` is the seam between the two: the document now
> carries `cryptoscan:quantum_status` with its basis (`REGISTRY_SHOR`,

> namespaced property, while the migration decision stays in the PQC engine —
> `algorithm_class`, `quantum_risk`, `migration_priority` and `migration_status`

> evidence enters, and it only escalates: runtime evidence outranks a capability,
> and a confidentiality purpose on a Shor-vulnerable algorithm is `IMMEDIATE`

> [Supported, existing, used: three answers for a key](143-cbom-kms-collectors.md)
> (**4 pass · 0 partial · 0 fail**, 20 probes) closes review item 11's key
> question. `cbom.kms_collectors` reads KMS/HSM inventory rows into metadata
> records — **never** key material, and a row carrying any is refused, not
> sanitised — then separates the three facts a CBOM is usually faked on:
> `VENDOR_DECLARED` (the module *supports* RSA-4096, no key implied),
> `CONFIGURED` (a key exists in the provider, no use implied) and
> `RUNTIME_OBSERVED` (an operation was recorded — the only one of the three that
> is usage). A configured key therefore promotes to `CONFIGURED` and no higher
> until an operation names it. Operations on keys nobody inventoried are refused,
> because that means the inventory is incomplete rather than the operation being
> wrong, and `posture` reports weak sizes, rotation past the bank's own policy
> age, and keys whose age is `UNKNOWN` instead of assuming them fresh.
> `POST /cbom/kms/keys` exposes it, typed and role-gated.
> [From "this library can do AES" to "this is an asset"](142-cbom-usage-promotion.md)
> (**4 pass · 0 partial · 0 fail**, 20 probes) closes review item 6 — the one that
> decides whether a CBOM can be trusted. `cbom.promotion` implements the chain the
> review asks for, capability → candidate → **evidence promotes**, and makes the
> boundary visible: a candidate becomes a CBOM asset only when an observing class
> (static, configuration, runtime, network) reports the algorithm; everything else
> is returned as a candidate and deliberately **kept out of the document**, because
> a document is what a reviewer reads as fact. Every promoted asset carries a
> promotion level — `CAPABILITY` < `STATIC`/`CONFIGURED` < `RUNTIME`/`NETWORK` <
> `VERIFIED` when the two independent mechanisms agree — plus the evidence ids that
> earned it. The document stays valid CycloneDX 1.5: standard fields carry the
> algorithm and its `algorithmProperties`, while every platform claim is a
> `cryptoscan:` property. An unattributable component (one with no evidence id) is
> refused rather than promoted quietly, and candidates are counted in metadata so a
> reader can see how much was left out. `POST /cbom/promote` exposes it.

## One end-to-end picture

```text
BANK APPROVAL: estate owner + information security + network/change team
      |
      v
Bank-controlled deployment: HTTPS ingress -> React console / API
                            PostgreSQL + Redis + optional graph service
                            workers / explicitly configured monitors
      |
      +-- approved Git or mounted source ----------> source collectors
      +-- approved IP:port / TLS services ---------> network collectors
      +-- permitted cloud control-plane APIs -----> cloud collectors
      +-- approved hardware metadata / events ----> hardware collectors
      +-- vendor declarations / supplied BOMs ----> vendor ingestion
      |
      v
Observed facts + declared facts, labelled by source and time
      -> durable scan/job/evidence/inventory records (path-dependent)
      -> normalization / identity / policy / recorded relationships
      -> SBOM | NBOM | CBOM | HBOM | VBOM | TechBOM views
      -> internal UI, snapshots, comparisons and controlled exports
      -> bank owner reviews -> bank change -> re-scan -> evidence of outcome
```

The source parser's isolated container is a special boundary: it receives an
admitted staged checkout, **has no network**, and returns bounded structured
results. The worker outside that parser may need Git, database and queue access.
Network/cloud routes can also execute inside the API process; permitting only
the worker to reach targets is not sufficient for those routes.

## The six names in one minute

| Product output | Bank question | Example |
|---|---|---|
| **SBOM — Software Bill of Materials** | What software components, versions and dependencies are present in the inspected input? | Application manifests/lockfiles, container packages, or supplied software BOMs |
| **NBOM — Network Bill of Materials** | What service is exposed, with which observed transport cryptography? | A partner gateway listener, negotiated TLS/cipher and served certificate |
| **CBOM — Cryptographic Bill of Materials** | Where is cryptography used, and what evidence supports it? | RSA key usage, AES mode, library and source location |
| **TechBOM — Technology Bill of Materials** | How do the technology inventory layers fit together? | Application, crypto, hardware and vendor projections plus recorded dependencies |
| **HBOM — Hardware Bill of Materials** | Which hardware and security components have actually been inventoried? | HSM model/firmware, TPM status, observation agent and last-seen time |
| **VBOM — Vendor Bill of Materials** | Which vendors/products supply crypto dependencies, and what do we know about them? | Vendor crypto declaration, dependent systems and due-diligence profile |

In this product **VBOM means Vendor BOM**, not Vulnerability BOM. Binary scanning
also has a separate vulnerability-BOM sidecar; the two must not be conflated.
TechBOM is not another independent scanner: its current general materializer
projects `sbom`, `cbom`, `hbom`, `vendor` and certificate metadata. NBOM remains a
separate network-evidence surface; do not promise a `nbom` export layer that the
TechBOM export API does not implement.

  not made production-approved by this walkthrough.

  **illustrative**. No customer target was scanned to write these documents.
