# Bank-side Performance capture → Twin simulation

**Boundary:** CryptoScan does not probe an arbitrary bank endpoint from the API. A bank-authorized collector reads Node Exporter, PostgreSQL Exporter or OTLP data inside the bank's approved scope, removes forbidden labels/payloads, retains the raw snapshot under bank custody, and submits a bounded capture to `POST /api/v1/performance/captures/import` using a tenant-bound writer/scanner key. The API stores normalized metric rows and a digest, **not** the raw exporter payload. It does not install a probe, run a load test, claim complete estate coverage, or select a migration wave.

## Admission and provenance

- The request names `tenant_id`, a **stored canonical** `asset_ref` (`app:` or `hw:`), `source_id`, `source_type` (`node_exporter`, `postgres_exporter`, `otlp`), `authorization_ref`, a timezone-aware `observed_at` and `payload.metrics`. At most 100 families / 1,000 samples and a 1 MiB JSON wire body are accepted. Each translated item reports accepted, duplicate or refusal; missing or stale measurements retain no numeric value.
- Counter-derived rates require `previous` and `previous_observed_at`; the interval comes from the two timestamps, never a caller-supplied denominator. A single counter snapshot cannot become throughput. Unsupported or ambiguous exporter families are refused, not mapped to a plausible unit.
- In production, `PERFORMANCE_CAPTURE_PUBLIC_KEY_FILE` must name an operator-approved Ed25519 **public** key at an absolute path outside the source tree — a single PEM key, or a JSON keyset `{"keys": [{"key_id", "public_key_pem"}, …]}`. In keyset form the attestation's `key_id` selects exactly one entry and an unlisted key_id is refused: a retiring bank signing key keeps verifying captures it signed until its entry is deliberately removed. The route refuses missing or unsigned production captures. The private signing key stays with the bank's collector/signing service, never in CryptoScan.
- `scripts/capture_signer.py` is the qualification aid for the bank's integrator: `keygen` writes a **TEST** Ed25519 keypair plus a trust-anchor keyset fragment, `sign` emits one import request body bound to the exact attestation schema, `verify` checks a body against an anchor before sending. It owns no network client or database, and captures signed with its test keys are engineering checks, never bank observations.
- Intake atomically commits normalized metrics and a tenant-owned `performance_capture_receipts` row. A repeat is idempotent. Metric `evidence_id` points to `signed-capture:<receipt_id>` (or `unverified-capture:<receipt_id>` in development); `GET /api/v1/performance/captures/<receipt_id>?tenant_id=<tenant>` returns the digest, public signature, signer/key ID, authorization reference, timestamp and accepted/refused counts, never raw exporter bytes. The bank must retain the original signed capture and approved public-key history for independent verification.
- The `attestation` object contains exactly `schema: cryptoscan.performance-capture-attestation/1`, `algorithm: Ed25519`, `key_id`, `issuer` and `signature` (strict base64). The signature covers compact, sorted-key UTF-8 JSON (`ensure_ascii=False`, no NaN) of the following fields: schema, algorithm, key_id, issuer, tenant_id, asset_ref, source_id, source_type, `observed_at` normalized to UTC ISO-8601 offset form, `previous_observed_at` normalized to UTC or null, authorization_ref, SHA-256 of the canonical current `payload`, and SHA-256 of canonical `previous` or null. The server reconstructs that body and verifies it against its site trust anchor. A valid signature authenticates the **source assertion and exact bytes**, not whether the exporter measured the bank or whether the collector was authorized. Retain bank authorization and the original capture independently.
- The direct metric ingestion endpoints remain available only in development/test. Production HTTP intake refuses them and requires bank-signed captures; trusted in-process integrations may still write internal metrics, but unsigned internal rows cannot become production simulation context. A caller cannot forge the reserved signed-capture provenance marker through direct HTTP intake.

## Simulation use

Select a **recorded CryptoLog CHANGE** on the same tenant and canonical asset, and one named metric/source. Supply non-overlapping, timezone-aware before and after windows (at most 31 days each) as `performance_context` on `POST /api/v1/estate/evidence/simulation/run`. The engine checks the event's stored hash, the registered metric unit, exact source and asset, sample budget (1,000/window) and bank capture provenance. At least five valid samples in each window are needed for a p95 comparison; missing, stale and partial-quality samples remain visible. An optional pair of approved controlled benchmark runs is compared only when hardware, software, provider, methodology, concurrency and sample count match. Benchmark **means** never become production p95.

The simulation first changes a **copy** of the Twin and re-projects the six BOMs. Performance appears in the response only as `purpose: SIMULATION_INPUT`, with `causation: UNPROVEN`, a recorded before/after measurement and an exact Twin identity-link state. An asset name match is never a link. This does **not** predict future PQC performance, approve a remediation, select a wave, or modify live estate state. If the bank has no signed captures, no exact link, or no recorded change, the result remains provisional, not evaluable, unlinked or refused with a reason.

## Before a bank pilot

The bank must approve the collector, exporter endpoint and timing, labels, signing key/trust anchor, target assets, change-event provenance, representative peak/failure windows, abort criteria and data residency. HSM/KMS provider measurements and any active load test require separate explicit approval and provider-specific adapters. The required CI contract tests the authenticated capture-to-Twin flow on SQLite; the PostgreSQL 15/16 migration lane repeats that same flow on a freshly migrated, disposable database and checks its no-skip JUnit result. Local fixtures and a signed capture from a test key are engineering checks, never bank observations or an independent performance qualification.
